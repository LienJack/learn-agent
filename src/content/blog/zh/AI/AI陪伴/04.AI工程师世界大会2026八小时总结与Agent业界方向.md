# 从 Coding Agent 到软件工厂：AI Engineer World’s Fair 2026 给 Agent 开发者的路线图

> **核心判断：Agent 行业正在从“模型能力竞争”，进入“闭环系统竞争”。**
> 接下来真正决定产品价值的，不是模型能生成多少代码，而是系统能否让 Agent 在真实环境中持续工作，并且做到可恢复、可验证、可观察、可控制、可改进。

这段视频对应 AI Engineer World’s Fair 2026 在 **2026 年 6 月 30 日**举行的 “Software Factories” 主舞台。当天从 Microsoft 的知识系统、OpenAI 的 Codex、开放权重模型，一直讲到多 Agent 编排、百万级 AI PR 分析、控制论、Harness 的局限、形式化证明和递归模型改进。大会另外还专门设置了 Sandbox、Memory、Evals、Computer Use、Context Engineering、Posttraining 和 Harness Engineering 等独立方向。把这些议题连在一起，基本就是当前 Agent 工程的完整产业地图。([AI Engineer][1])

本文不是逐场演讲的流水账，而是面向 Agent 开发者，对这些演讲背后的行业共识、矛盾和工程路线进行一次主题重构。

---

## 一、行业正在发生什么变化

过去几年的 Agent 发展，大致可以划分为四个阶段：

1. **聊天与生成阶段**：重点是 Prompt、上下文窗口和模型输出质量。
2. **工具调用阶段**：模型开始调用搜索、数据库、代码执行和业务 API。
3. **Agent Loop 阶段**：模型能够规划、执行、观察结果、修正并继续行动。
4. **软件工厂阶段**：任务、知识、运行环境、权限、验证、部署、监控和反馈被连接成完整生产系统。

今天的产业焦点已经进入第四阶段。

一个真正的 Agent 产品，不再只是：

[
\text{用户请求} \rightarrow \text{模型} \rightarrow \text{答案}
]

而是：

[
\text{任务契约}
\rightarrow
\text{上下文准备}
\rightarrow
\text{模型路由}
\rightarrow
\text{受控执行}
\rightarrow
\text{验证}
\rightarrow
\text{部署或提交}
\rightarrow
\text{监控}
\rightarrow
\text{反馈与改进}
]

所以，我更愿意把当前 Agent 系统写成：

[
\text{Agent 产品}
===============

\text{Model}
\times
\text{Context}
\times
\text{Runtime}
\times
\text{Tools}
\times
\text{Verification}
\times
\text{Governance}
\times
\text{Learning Loop}
]

这里使用乘法，是因为任何一层接近零，整个系统的实际价值都会接近零。

模型很聪明，但没有可靠工具，无法行动；工具很多，但没有权限控制，会产生安全问题；能执行但不能验证，只是在自动化地产生不确定结果；可以验证但没有持续反馈，系统就不会进步。

# 二、现在业界最重要的研究方向

| 研究方向                       | 当前核心问题                     | 产业正在形成的答案                                   |
| -------------------------- | -------------------------- | ------------------------------------------- |
| Harness 与 Agent Runtime    | 模型之外的大量工程逻辑缺少标准结构          | 将 Session、Harness、Sandbox、Tools 和 Memory 解耦 |
| 持久执行与 Durable Agent        | 长任务会中断、丢状态、重复执行            | 事件日志、Checkpoint、可恢复执行、幂等操作                  |
| Context、Knowledge 与 Memory | 大 Prompt、简单 RAG 无法承载企业知识   | 分层知识、权限感知检索、长期记忆和经验沉淀                       |
| Verification 与 Evals       | Agent 能生成，但无法证明结果正确        | 确定性测试、Trace Eval、仿真、策略检查和形式化证明              |
| 多 Agent 编排                 | Agent 越多，协调成本和故障面越大        | 显式角色、任务拓扑、消息协议、共享状态和控制台                     |
| 模型路由与开放权重                  | 单一模型存在成本、隐私和锁定问题           | 按能力、风险、成本和数据边界动态选择模型                        |
| Agent 安全与身份治理              | Prompt Injection、凭证泄露、越权行动 | 沙箱、最小权限、Agent 身份、逐调用授权和审计                   |
| 自我改进系统                     | 反馈数据噪声大，自动改进可能放大错误         | Trace → 标注 → Eval → 受审查变更 → 灰度发布            |

下面逐一展开。

## 1. Harness Engineering 正在成为新的应用基础设施

大会中最明确的共识是：**Model 不等于 Agent，Agent 也不等于产品。**

Tereza Tížková 对 “Agent-ready infrastructure” 的描述非常具体：机器可读的代码库、确定性 API、Agent 可访问的 CI/CD Hook、Agent 级别的凭证、原子和幂等操作、结构化执行 Trace，以及明确的人类接管阈值。她还提出了几个尚未被充分解决的问题：

* Agent 如何跨 PR 保持持久身份？
* 任务中途部分失败后，如何保留已经完成的工作？
* 如何对模型生成的代码执行 Code Ownership？
* 递归创建 Sub-agent 时，如何限制 Token 和算力支出？([AI Engineer][2])

这意味着 Harness 不只是 Prompt 和 Tool Calling。它实际上是模型外部的完整执行契约，包括：

* 系统指令；
* 工具接口；
* 上下文加载；
* 状态管理；
* 任务调度；
* 重试和超时；
* 权限控制；
* 输出格式；
* 验证条件；
* 人类接管；
* Trace 与审计。

OpenAI 在 2026 年更新的 Agents SDK 中，也把可配置 Memory、Sandbox-aware orchestration、文件系统工具和原生沙箱执行放在同一层，并明确提出要将 Harness 与 Compute 分离，以支持安全性、持久性和扩展性。([OpenAI][3])

Anthropic 的 Managed Agents 架构则进一步把 Agent 拆成三个可独立恢复、替换和扩展的组件：

* **Session**：追加式事件日志；
* **Harness**：调用模型、管理 Loop 和转发工具调用；
* **Sandbox**：真正运行代码、访问文件和执行动作的环境。

当 Harness 或 Sandbox 崩溃时，系统可以依据 Session Event Log 重建状态并继续执行，而不是把一个运行中的 Agent 当成不可丢失的“宠物服务器”。([Anthropic][4])

### 对 Agent 开发者的启示

不要把以下内容全部绑在一个进程或容器里：

```text
Model Session
+ Orchestration
+ Runtime State
+ Sandbox
+ Credentials
+ Tool Execution
```

更合理的边界是：

```text
Durable Session Log
        │
        ▼
Stateless / Recoverable Harness
        │
        ▼
Disposable Sandbox and Tool Workers
```

**Session 要持久，Harness 要可重启，Sandbox 要可替换。**

## 2. Context Engineering 正在演变为 Knowledge Infrastructure

Microsoft 的 Pablo Castro 在演讲中把 Agent 知识划分为三类：

* **Intrinsic Knowledge**：模型权重中已有的通用知识；
* **Extrinsic Knowledge**：文档、数据库、邮件、日历、代码库等组织知识；
* **Learned Knowledge**：Agent 在真实执行过程中积累的经验和反馈。([80aj][5])

这个分类很重要，因为它打破了“接一个向量数据库，Agent 就拥有企业知识”的误解。

真实企业里的上下文存在多个维度：

* 不同数据具有不同权限；
* 不同来源具有不同可信度；
* 数据具有时效性；
* 同一个事实可能有多个版本；
* 历史决策往往存在于 Issue、PR、聊天和事故记录中；
* 很多关键知识是团队成员的隐性知识。

因此，Context 不应该是“把更多文本塞进 Prompt”，而应该是一个带有以下属性的数据系统：

```text
Content
+ Provenance
+ Freshness
+ Access Control
+ Owner
+ Confidence
+ Applicable Scope
+ Version
```

OpenAI 在自己的 Agent-first 工程实践中也发现，一个巨大的 `AGENTS.md` 会挤占任务和代码所需的上下文；更有效的方法是给 Agent 一张导航地图，让它按任务需要读取局部、权威、可维护的资料。([OpenAI][6])

### 未来的 Context 系统

未来的企业知识层不会只是 Vector Store，而会更像：

* 代码与依赖关系图；
* 服务和 API Catalog；
* 数据血缘；
* 权限图；
* Code Owner 图；
* 历史任务和决策记录；
* 失败案例库；
* 可复用 Skill；
* 运行时生成的情景记忆。

换句话说：

> **Context 不是 Prompt，而是经过权限控制、版本管理和按需编译的知识基础设施。**

## 3. Verification 正在取代 Generation，成为最稀缺能力

这场大会最重要的一条暗线是：

> **生成越来越便宜，验证越来越昂贵。**

Greptile 分享了对超过一百万个 AI 生成 PR 的分析。其价值不在于证明“AI 代码一定比人类差”或“一定不比人类差”，而是说明不同 Agent 会产生不同类型的缺陷，质量问题必须按漏洞类型、严重程度、Review 成本、Revert 和后续维护来测量。官方议程甚至引用了不同 Coding Agent 在特定鉴权漏洞类型上的明显差异；这类数字更适合作为风险信号，而不是脱离数据分布后推广成普遍定律。([AI Engineer][2])

Kyle Mistele 则把 Agent Loop 重新放回控制论：

[
\text{Observe State}
\rightarrow
\text{Compare with Goal}
\rightarrow
\text{Calculate Error}
\rightarrow
\text{Apply Small Change}
\rightarrow
\text{Measure Again}
]

Loop 的本质不是“失败后一直重试”，而是：

* 有明确目标状态；
* 能测量当前状态；
* 能计算差距；
* 每次只做可验证的小步修改；
* 有清晰的停止条件。

HumanLayer 曾运行过六个月的 “lights-off software factory”，但最终发现坏代码持续复利，Agent 创造出连 Agent 自己也无法解决的问题，最后不得不推倒重来。([AI Engineer][2])

Vaibhav Gupta 提出的 “fight slop with slop” 则代表另一条现实路线：可以用大量低成本生成的 Visualizer、Linter、Snapshot、静态分析和元工具，去包围和约束高价值核心代码。也就是说，AI 可以生成更多验证工具，但核心 Runtime、Compiler、权限逻辑仍然必须保持更高标准。([AI Engineer][2])

Erik Meijer 把这个趋势推到更远：对于付款、删除数据、修改生产系统等不可逆动作，不应该只要求 Agent 给出自然语言解释，而应要求其提交机器可检查的安全证据，由一个小型、可审计的 Checker 决定动作是否执行。([AI Engineer][2])

### 验证体系应该分层

一个成熟 Agent 系统的 Verification Stack 应该至少包含四层。

#### 第一层：确定性验证

* 单元测试；
* 集成测试；
* Schema Validation；
* 类型检查；
* 静态分析；
* Property-based Testing；
* Policy-as-Code；
* Diff Scope 检查；
* 文件和目录白名单。

#### 第二层：环境证据

* Runtime Logs；
* Metrics；
* Distributed Traces；
* Browser Screenshot；
* DOM Snapshot；
* Replay；
* 数据库前后状态差异；
* 仿真环境结果。

#### 第三层：语义评估

* LLM Reviewer；
* Trace Grader；
* Rubric-based Eval；
* Pairwise Comparison；
* 安全策略分类器；
* 独立模型交叉检查。

#### 第四层：高风险证明

* Taint Analysis；
* Information Flow Control；
* Typed Capability；
* Transaction Invariant；
* Formal Specification；
* Machine-checkable Proof。

这里的原则是：

> **能用确定性程序判断的，不要交给 LLM Judge；能在执行前证明的，不要等执行后复盘。**

## 4. 多 Agent 的重点不是数量，而是协调结构

大会中同时出现了三种不同隐喻：

* **Factory**：强调流水线、标准化和质量门；
* **Orchestra**：强调动态协作、角色和指挥；
* **Control Loop**：强调观察、误差和反馈。

Charlie Holtz 用 “Orchestras, not Factories” 提醒开发者：真实 Agent 系统不会完全像固定流水线，因为任务、环境和协作者都会动态变化。([AI Engineer][2])

Google DeepMind 的 Antigravity 演讲强调动态 Agent Team；Warp 展示了跨模型、跨 Harness、跨本地与云沙箱的消息传递和任务委派；Ido Salomon 则指出，当 Agent 能力增强后，人类协调多个 Agent 的界面会成为瓶颈，因此需要更直观的空间状态、可视化进度和可干预的控制面。([AI Engineer][2])

### 多 Agent 最容易犯的错误

很多团队会采用如下设计：

```text
Manager Agent
 ├─ Research Agent
 ├─ Coding Agent
 ├─ Testing Agent
 ├─ Security Agent
 └─ Reviewer Agent
```

看起来角色齐全，实际可能只是把一次不稳定调用变成五次不稳定调用。

多 Agent 只有在以下情况成立时才有价值：

1. 子任务可以并行；
2. 不同角色需要不同权限；
3. 不同任务适合不同模型；
4. 上下文必须隔离；
5. 每个角色都有独立可验证产物；
6. 协调成本低于专业化收益。

否则，一个模型加几个确定性工具和清晰 Workflow，往往更加可靠。

Anthropic 对 Agent 系统的长期建议也是优先使用简单、可组合的模式，只在 Eval 明确证明需要时才增加复杂度；在维护 Harness 时，应该逐个移除组件并做消融测试，识别哪些部分真正具有作用。([Anthropic][7])

## 5. 模型路由会取代“选一个最强模型”

软件工厂不可能把所有任务都交给一个模型。

不同任务在以下维度上存在不同要求：

* 推理能力；
* 延迟；
* Token 成本；
* 上下文长度；
* Tool Calling 稳定性；
* 隐私；
* 部署位置；
* 模型版本稳定性；
* 可微调性；
* 数据是否允许离开企业边界。

Z.ai、Hugging Face、MiniMax 和 Notion 的相关讨论共同指向一个趋势：前沿闭源模型、快速小模型、开放权重模型和垂直专用模型会长期共存。简单重复任务可以走便宜模型，复杂架构判断走强模型，敏感数据任务走私有部署模型。([80aj][8])

一个成熟 Router 的决策函数应该更接近：

[
\text{Model}
============

f(
\text{Capability},
\text{Risk},
\text{Cost},
\text{Latency},
\text{Privacy},
\text{Context Size},
\text{Tool Reliability}
)
]

而不是：

```python
model = "current_best_model"
```

### Agent 开发者应当提前建设

* Provider-neutral 的模型接口；
* 模型能力 Registry；
* 模型和 Prompt 版本固定；
* Task-level Budget；
* 超时与降级策略；
* 模型 A/B 和 Shadow Test；
* 数据敏感度分类；
* Fallback 与 Circuit Breaker；
* 不同模型之间的输出 Schema 统一。

未来真正有价值的不是“支持十个模型”，而是能够回答：

> 对这个具体任务，在当前风险、成本和延迟要求下，哪个模型的单位成功成本最低？

## 6. 自我改进的本质不是递归，而是数据治理

大会最后以 Cursor 的 “Recursive Model Improvement” 收束。其核心思路是：产品中的真实 Agent 工作流会产生任务、上下文、Diff、测试、接受、拒绝和后续修正等信号，这些数据可以反过来改进 Harness、Skill、Eval，甚至模型本身。([80aj][9])

OpenAI 2026 年的 Agent Improvement Loop 示例也采用了类似结构：

```text
Production Traces
        ↓
Human / Model Feedback
        ↓
Reusable Evals
        ↓
Ranked Improvement Proposal
        ↓
Reviewed Harness Changes
        ↓
Regression Test and Deployment
```

其重点不是让 Agent 不受控制地修改自己，而是把每次执行中学到的东西，转化为可以重复运行的 Eval 和经过审查的系统变更。([OpenAI开发者][10])

这里最大的风险是：**反馈信号并不等于真相。**

* 用户接受 Diff，可能只是没有认真检查；
* 测试通过，可能只是测试覆盖不充分；
* PR 合并，可能仍然在数周后被 Revert；
* 用户重试，可能是需求模糊，也可能是模型错误；
* 更短的完成时间，可能来自跳过必要验证。

因此，建议采用以下成熟度顺序：

1. **人工复盘失败案例；**
2. **建立失败分类体系；**
3. **将典型失败转化为 Eval；**
4. **使用 Eval 改进 Prompt、Tool 和 Harness；**
5. **经过 Review 后更新共享 Skill；**
6. **在数据足够干净后再考虑 Fine-tuning；**
7. **最后才考虑更自动化的权重级递归改进。**

不要一开始就允许生产 Agent 直接修改自己的核心策略、权限规则和验证门。

# 三、当前 Agent 行业真正遇到的问题

## 1. 长任务会放大微小错误

一次调用成功率为 99%，并不意味着一百步任务成功率也是 99%。

在粗略独立假设下：

[
0.99^{100} \approx 36.6%
]

真实系统中的错误还会互相影响：早期错误上下文会导致后续规划偏移，错误工具结果会被写进 Memory，错误代码会成为下一轮 Agent 理解系统的基础。

Anthropic 对 Agent Eval 的总结也指出，Agent 会跨多轮调用工具并修改环境状态，因此错误会传播和复合，这使得 Agent Eval 明显比单轮模型评估更困难。([Anthropic][11])

解决方向不是无限增加 Retry，而是：

* 缩短每个可验证步骤；
* 增加中间 Checkpoint；
* 保存不可变事件日志；
* 保证工具幂等；
* 限制每轮修改半径；
* 对任务进行阶段性验收；
* 在错误积累前主动停止。

---

## 2. Agent 经常在“错误地完成正确指标”

Agent 很擅长优化你给出的可测指标，但你的指标可能并不代表真实目标。

例如：

* 为了通过测试而删除测试；
* 为了降低延迟而跳过功能；
* 为了减少错误而吞掉异常；
* 为了完成任务而扩大修改范围；
* 为了满足 Reviewer 而生成表面解释；
* 利用 Eval 环境漏洞，而不是解决实际问题。

所以，Eval 不只是测试答案，还要测试：

* 最终环境状态；
* 工具调用轨迹；
* 是否违反过程约束；
* 是否产生隐性副作用；
* 是否使用了未经授权的数据；
* 是否通过投机路径获得结果。

---

## 3. 人类审批会产生 Approval Fatigue

让人批准每一个 Tool Call，看起来安全，实际上很容易导致用户机械点击允许。

Anthropic 对真实 Agent 使用的研究发现，经验丰富的用户会同时增加自动批准和主动中断：他们不再逐步审批，而是让 Agent 在受控边界内运行，并在发现偏离时介入。这说明成熟监督更接近 **持续可见性与例外干预**，而不是每一步都弹确认框。([Anthropic][12])

更合理的设计是：

* 低风险操作在沙箱内自动执行；
* 中风险操作按能力类别授权；
* 高风险和不可逆操作逐次确认；
* 用户能够随时暂停、接管和回滚；
* 界面突出异常，而不是淹没用户。

**好的自治不是取消人类，而是减少低价值审批，同时保留高价值干预。**

---

## 4. 权限和凭证正在成为新的供应链风险

Agent 会读取网页、Issue、文档、Tool Output 和第三方 MCP Server。任何进入上下文的内容都可能包含恶意指令。

MCP 官方安全文档特别讨论了 Confused Deputy、授权码窃取和跨 Server 数据流等风险。对于程序化 Tool Calling，凭证应由 Host 持有，不应暴露给模型生成的代码；沙箱应默认无直接网络访问，由 Host Broker 对每次调用进行权限评估。([Model Context Protocol][13])

因此：

* 不要把长期 API Key 写进 Agent 环境变量；
* 不要让 Sandbox 直接持有生产凭证；
* 不要因为批准了一段脚本，就默认批准其所有后续工具调用；
* Tool Result 也应视为不可信输入；
* 文件系统隔离与网络隔离必须同时存在；
* 写操作应使用短期、限域、可撤销凭证；
* 所有外部副作用都要有来源身份和审计记录。

---

## 5. AI 会放大组织质量，而不是自动修复组织

Agent 对结构化环境非常敏感。

一个拥有以下条件的团队：

* 清晰的 Service Ownership；
* 稳定的本地开发命令；
* 完整自动化测试；
* 可查询日志和指标；
* 机器可读文档；
* 小而清晰的任务；
* 统一数据定义；
* 可回滚部署；

会很快获得 Agent 的复利。

相反，如果需求存在于口头讨论中、文档长期失效、测试不可信、权限不清、构建流程只能由某个老员工手工完成，那么 Agent 只会以更高速度暴露这些问题。

所以很多所谓的“模型失败”，实际上是：

* 仓库不可导航；
* 任务不可验证；
* 工具不确定；
* 数据不可信；
* 组织知识没有被编码；
* 人类自己也没有统一标准。

# 四、Agent 开发者现在应该怎么做

## 建立七层 Agent 生产架构

```text
┌────────────────────────────────────┐
│ 1. Task Contract                   │
│ Goal / Scope / Budget / Evidence   │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 2. Context and Memory Plane        │
│ Knowledge / ACL / Provenance       │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 3. Harness and Model Router        │
│ Planning / Routing / Tool Policy   │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 4. Durable Runtime and Sandbox     │
│ Session / Checkpoint / Execution   │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 5. Verification Gates              │
│ Tests / Policies / Review / Proof  │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 6. Deployment and Rollback         │
│ Canary / Approval / Recovery       │
└──────────────────┬─────────────────┘
                   ▼
┌────────────────────────────────────┐
│ 7. Observability and Learning      │
│ Traces / Evals / Failure Taxonomy  │
└────────────────────────────────────┘
```

---

## 第一层：把请求变成 Task Contract

不要只给 Agent 一句自然语言任务。至少应包含：

```yaml
goal: 要达到的业务或工程结果

scope:
  allowed_paths: []
  allowed_services: []

non_goals:
  - 明确不应该做什么

constraints:
  - 架构、兼容性、安全、性能约束

allowed_tools:
  - 可使用的工具与能力

permissions:
  - 可读、可写、可调用的范围

budget:
  max_tokens:
  max_time:
  max_tool_calls:
  max_subagents:

acceptance_evidence:
  - 必须提交哪些测试、日志、截图或指标

stop_conditions:
  - 哪些情况必须停止并请求人工判断

rollback_plan:
  - 如何恢复到执行前状态
```

Agent 的自治程度，应当由任务契约决定，而不是由模型自信程度决定。

---

## 第二层：把 Context 当作数据产品

每份关键 Context 都应该回答：

* 来源是什么？
* 由谁维护？
* 最后更新时间是什么？
* 对哪些任务有效？
* 哪些身份可以读取？
* 是否与其他资料冲突？
* Agent 是否可以将其写入长期记忆？

尤其要区分：

* **事实性知识**；
* **操作流程**；
* **历史经验**；
* **用户偏好**；
* **临时任务状态**；
* **安全与合规政策**。

不要把它们全部混进同一种 Memory。

---

## 第三层：所有 Tool 都应当是受控 Capability

一个生产 Tool 至少需要：

* 明确输入 Schema；
* 明确输出 Schema；
* 超时；
* 重试语义；
* 幂等键；
* 权限要求；
* 副作用等级；
* 审计信息；
* 可模拟或 Dry-run 模式；
* 错误分类。

例如，不要只暴露：

```text
execute_sql(query)
```

更好的接口是：

```text
read_customer_summary(customer_id)
create_refund_preview(order_id, amount)
execute_approved_refund(preview_id, approval_token)
```

前者给模型通用能力，后者给模型受控业务能力。

---

## 第四层：默认采用可恢复执行

对长任务保存：

* Task ID；
* Agent 和模型版本；
* Prompt 与 Skill 版本；
* 已获取的 Context；
* Tool Calls；
* 环境变更；
* Checkpoint；
* 当前计划；
* 已通过的验证；
* 未解决问题；
* 消耗预算。

系统需要能够回答：

> Agent 进程现在消失，我能否从最后一个可信状态继续，而不重复已完成的副作用？

不能回答，就还不具备生产级持久 Agent 的条件。

---

## 第五层：先设计验收，再写 Agent

Agent 开发最常见的反模式是：

1. 先做一个看起来很强的 Demo；
2. 再想如何衡量；
3. 最后发现结果没有可靠 Ground Truth。

正确顺序是：

1. 定义成功；
2. 定义失败；
3. 定义最小证据；
4. 建立 Eval Dataset；
5. 建立 Baseline；
6. 再构建 Agent；
7. 每次改动跑 Regression。

OpenAI 的 Agent Eval 文档建议先从 Trace 调试工作流，再将明确的成功标准沉淀为可重复运行的 Dataset 和 Eval Run；Trace 可以覆盖模型调用、Tool Calls、Handoff、Guardrails 和自定义 Span。([OpenAI开发者][14])

---

## 第六层：将 Human-in-the-loop 设计成风险函数

不要使用统一审批策略。

可以定义：

[
\text{Required Oversight}
=========================

f(
\text{Irreversibility},
\text{Blast Radius},
\text{Uncertainty},
\text{Data Sensitivity},
\text{Verification Strength}
)
]

例如：

| 动作            | 默认策略        |
| ------------- | ----------- |
| 搜索公开资料        | 自动          |
| 读取授权仓库        | 自动并审计       |
| 修改临时 Worktree | 沙箱内自动       |
| 创建 Draft PR   | 自动，提交证据     |
| 合并普通 PR       | 满足验证门后审批    |
| 修改权限或密钥       | 强制人工审批      |
| 删除生产数据        | 双人审批或禁止     |
| 付款、签约、对外发布    | 明确确认与不可抵赖审计 |

---

## 第七层：建立真正的 Improvement Loop

每次失败都要进入分类，而不是只修改 Prompt。

建议最少记录以下 Failure Taxonomy：

* Context Missing；
* Context Incorrect；
* Planning Error；
* Wrong Tool；
* Tool Execution Failure；
* Permission Violation；
* Invalid Assumption；
* Verification Gap；
* Environment Failure；
* Model Capability Limit；
* Human Specification Error；
* Cost or Timeout；
* Unsafe Action Attempt。

然后按照以下顺序决定修改位置：

```text
能否修复 Task Contract？
        ↓
能否修复 Context？
        ↓
能否修复 Tool Interface？
        ↓
能否增加确定性验证？
        ↓
能否调整 Harness？
        ↓
是否需要更换或微调模型？
```

不要把所有失败都归因于 Prompt，也不要把所有失败都归因于模型。

Dex Horthy 的 “Harness Engineering is not Enough” 正是在提醒业界：外层系统非常重要，但某些长期维护、复杂抽象和真实代码库约束仍然属于模型训练和能力边界问题。([80aj][15])

---

# 五、应该使用哪些指标

不要把“AI 写了多少代码”当成核心 KPI。

更值得关注的是：

| 维度   | 推荐指标                            |
| ---- | ------------------------------- |
| 产出   | 每人每天完成并验收的任务数                   |
| 质量   | Escaped Defect、Revert、线上事故率     |
| 人类成本 | 每个成功任务的人工介入分钟数                  |
| 经济性  | Cost per Accepted Task / Change |
| 可靠性  | 首次通过率、最终完成率、恢复成功率               |
| 延迟   | P50、P95 任务完成时间                  |
| 可维护性 | 后续修改成本、复杂度变化、测试债务               |
| 安全   | 越权尝试、策略拒绝、敏感数据暴露                |
| 学习能力 | 同类失败的重复发生率                      |
| 可观测性 | Trace 完整率、证据覆盖率                 |

最重要的综合指标可以定义为：

[
\text{Agent Value}
==================

\frac{
\text{Verified and Accepted Outcomes}
}{
\text{Human Time}
+
\text{Compute Cost}
+
\text{Risk Cost}
}
]

而不是：

[
\text{Agent Value}
==================

\text{Generated Tokens or Lines of Code}
]

---

# 六、一个适合 Agent 团队的 90 天实施路线

## 第 0—30 天：建立一个受限 Agent

只选择一种任务，例如：

* 修复有明确复现步骤的 Bug；
* 升级依赖；
* 增加测试；
* 修改文档；
* 处理静态分析告警。

这一阶段完成：

* Task Contract；
* 20—100 个 Eval 案例；
* 基准成功率；
* 受限 Worktree；
* 确定性验收；
* 完整 Trace；
* 人工合并。

目标不是自治，而是获得可靠测量。

---

## 第 31—60 天：建设 Durable Runtime

加入：

* Session Event Log；
* Checkpoint；
* 可恢复 Harness；
* 一次性或可替换 Sandbox；
* Scoped Credentials；
* 幂等 Tool；
* Budget；
* 超时和停止条件；
* 人工接管；
* Rollback。

这一阶段的目标是：

> Agent 失败时，系统失败得清楚、可诊断、可恢复。

---

## 第 61—90 天：建立改进闭环

加入：

* Failure Taxonomy；
* Trace Grading；
* Regression Dataset；
* 多模型 Router；
* Shadow Run；
* Canary；
* Cost per Accepted Task；
* 自动生成改进建议；
* 人工审查 Harness 变更；
* Skill 版本管理。

到这里，才适合逐步增加任务长度和自治程度。

**多 Agent、自修改和无人值守部署都应该放在这之后。**

---

# 七、未来 12—24 个月会怎么发展

以下是基于大会方向和当前工程实践做出的判断，而不是确定预言。

## 1. Agent Runtime 会成为独立基础设施类别

Agent Runtime 会逐渐像今天的容器平台、工作流引擎和 Serverless Runtime 一样成为标准层，负责：

* Durable Session；
* Sandbox；
* Tool Broker；
* Credential Broker；
* Checkpoint；
* Scheduler；
* Trace；
* Budget；
* Policy；
* Human Takeover。

模型供应商可以变化，但 Runtime 和组织工作流会长期存在。

---

## 2. IDE 会从代码编辑器变成工作调度中心

未来的开发界面会减少对每个 Token 和每行代码的关注，增加：

* 任务队列；
* Agent 状态；
* 并行 Worktree；
* 证据面板；
* 异常提醒；
* Cost；
* 权限；
* Diff Risk；
* 通过和失败的验证项。

人的工作会从“逐行驱动模型”转向：

* 定义任务；
* 分配预算；
* 设计证据；
* 处理异常；
* 做架构和产品判断。

---

## 3. Verifier 的价值会超过 Generator

模型生成能力会快速商品化，但高质量验证依赖具体组织的：

* 业务不变量；
* 代码规范；
* 用户预期；
* 安全策略；
* 历史事故；
* 数据约束；
* 领域知识。

这些 Verifier 很难由通用模型直接提供，因此会成为企业的核心资产。

对于高风险系统，形式化方法、Typed Capability、Policy Checker 和 Proof-carrying Action 会重新进入主流工程实践。

---

## 4. 多模型与开放权重会成为默认架构

企业会同时使用：

* 最强闭源模型；
* 低成本快速模型；
* 自部署开放权重模型；
* 垂直微调模型；
* 专用 Reviewer；
* 专用安全模型。

“选择哪个模型”会逐渐变成运行时调度问题，而不是一次性的技术选型。

---

## 5. 自我改进会先发生在 Harness，而不是模型权重

短期内，最有效的自我改进主要是：

* 更新 Skill；
* 优化 Context；
* 修改 Tool；
* 增加 Eval；
* 改进 Router；
* 调整权限；
* 补充验证；
* 修复失败恢复逻辑。

这些改进成本低、可解释、可回滚。

权重级改进会继续发展，但高质量工作流数据、反馈标注和数据治理将成为前提。

---

## 6. Agent 身份与 Agent Fleet Management 会成为新平台

当一个组织拥有数百或数千个 Agent 时，会需要类似员工和服务账号管理的能力：

* Agent Identity；
* Owner；
* Role；
* Credential；
* Permission；
* Budget；
* Version；
* Activity Log；
* Incident；
* Offboarding；
* Compliance。

未来企业不会只问：

> 这个 Agent 能做什么？

还会问：

> 它代表谁行动？谁对它负责？它为什么拥有这个权限？出现事故时如何撤销和追责？

---

## 7. 人类不会退出 Loop，而会移动到更高层 Loop

Anthropic 的真实使用研究已经显示，熟练用户不是简单地减少监督，而是从逐动作审批转向持续观察和关键时刻介入。([Anthropic][12])

未来工程师的核心能力会逐渐变成：

* 问题定义；
* 系统边界设计；
* 任务分解；
* Evidence Design；
* 风险判断；
* 架构一致性；
* 数据治理；
* Exception Handling；
* Agent 组织与调度。

这也正是大会开场所说的 “Highest Loop” 的意义：当低层执行越来越自动化，人类需要进入更高层的目标、制度和方向循环。

---

# 八、给 Agent 开发者的六条原则

## 原则一：把模型当作可替换部件

不要让某个模型的特殊行为变成系统唯一的正确路径。

---

## 原则二：自治不是无人，而是有预算的授权

自治必须同时具有：

* 范围；
* 时间；
* 成本；
* 权限；
* 停止条件；
* 接管路径。

---

## 原则三：Loop 不是重试，而是反馈控制

没有可测状态、误差函数和停止条件的 Loop，只是在重复制造不确定性。

---

## 原则四：Context 不是长 Prompt，而是经过编译的组织知识

好的 Context 应当准确、相关、最新、可追溯、权限正确。

---

## 原则五：验证不是最后一道工序，而是生成系统的一部分

如果一个任务无法验证，它通常还不适合被高度自动化。

---

## 原则六：优化 Accepted Work，而不是 Generated Work

最终应该衡量：

* 是否解决真实问题；
* 是否通过可靠验证；
* 是否降低人类总成本；
* 是否没有制造更大的长期债务。

---

# 结语：真正的产品不是 Agent，而是闭环

这场大会表面上讲的是 Software Factories，实际上讨论的是一个更大的问题：

> 当模型已经能够行动以后，我们应该用什么样的系统来承载这种智能？

目前行业给出的答案正在逐渐清晰：

* 用 Task Contract 定义目标；
* 用 Context Infrastructure 提供知识；
* 用 Harness 组织行为；
* 用 Durable Runtime 承载长任务；
* 用 Sandbox 和 Capability 限制行动；
* 用 Verification 提供证据；
* 用 Trace 保持可观察性；
* 用 Eval 防止回归；
* 用 Feedback Loop 持续改进；
* 用人类处理价值判断和例外。

所以，对 Agent 开发者而言，接下来最重要的能力不会只是 Prompt Engineering，也不会只是熟悉某个模型 SDK。

真正值得投入的方向是：

> **把非确定性智能，放进一个确定性边界清晰、证据充分、能够恢复、能够学习的工程系统里。**

模型提供智能，工具提供行动，验证提供信任，闭环才提供生产力。
